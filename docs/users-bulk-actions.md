# Users: фильтры и массовые действия

Требуется backend PR с API `/cabinet/admin/user-bulk-operations`, журналом
в PostgreSQL и миграцией 0132. Сначала обновить backend, затем этот frontend.
Продакшен в рамках разработки и тестирования не использовался.

## Работа администратора

1. Открыть Users. Расширенные фильтры по умолчанию свёрнуты. Дата означает
   пересечение календарного дня в TIMEZONE приложения **по текущим срокам**;
   это не подтверждённая история активности. Ограничение явно указано под фильтром.
   ID подходящих подписок отображаются в строке.
2. Выбрать пользователей по одному или чекбоксом страницы. Выбор сохраняется
   между страницами. При смене фильтра, поиска или сортировки он сбрасывается.
3. Для всей выборки нажать «Выбрать всех по текущим фильтрам». Сервер сохраняет
   состав целей и возвращает счётчики; карточки всех пользователей не скачиваются.
   Новые пользователи и подписки в старый выбор не добавляются.
4. Выбрать 10/50/100 GB, продление или сокращение на положительное число дней.
   Предпросмотр показывает точные числа уникальных пользователей и подписок,
   пропуски с причинами и последствия реактивации. Обрабатываются все подходящие
   подписки, а не произвольная первая.
5. Подтвердить операцию. Двойной клик заблокирован; параметры и состав связаны
   с сохранённым ID операции. При смене действия используется исходный снимок целей.
6. Вверху Users отображается общий прогресс. Браузер запрашивает пачки строго
   последовательно. SSE читает серверный журнал каждые две секунды и закрывается
   после окончания. Пользователь обработан только после всех своих подписок;
   отдельно видны частичные успехи, отмены и неопределённые результаты.
7. «Отменить оставшихся» требует подтверждения. Выполненные изменения сохраняются;
   уже отправленный запрос может завершиться позднее.
8. После закрытия страницы, сбоя или перезапуска автоматически новые пачки
   не запускаются. Операция восстанавливается из журнала; нажать «Продолжить».
   Успешные и неопределённые цели не повторяются. Ошибки выдаются страницами
   по 50 записей и требуют ручной проверки БД/панели.

Для новых действий и просмотра журнала нужны `users:read` и
`bulk_actions:execute`. Администратор только с чтением видит фильтры без
чекбоксов и кнопок массовых действий. Локальная сеть, Redis или браузерное
хранилище не являются источником истины для прогресса.

При потере соединения или 409 нужно обновить состояние существующей операции.
Не создавать повторное начисление для тех же пользователей. Продолжение
после неопределённого исхода касается только оставшихся целей.

## Проверки

```sh
npm ci --ignore-scripts
npm run type-check
npm run build
npx playwright install chromium
npm run test:users-bulk
```

Для установленного Chrome можно передать
`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/полный/путь/к/Chrome`.

Браузерные тесты запускают настоящий компонент AdminUsers в fixture с
подменённым API. Проверяются выбор страниц, промежуточный чекбокс, сброс фильтров,
снимок всей выборки, точные числа подтверждения, двойной клик, несколько пачек,
отмена, восстановление без автоматического запуска, неопределённые результаты,
права чтения и мобильная ширина. Эти тесты не обращаются к Remnawave и не заменяют
проверку парных PR на стенде. CI запускает их отдельным workflow.

На стенде проверить парные изменения с реальным PostgreSQL и тестовой панелью:
начисление пакетов, реактивацию, несколько подписок, сокращение до истечения,
остановку во время запроса, перезапуск backend и конкурирующее продолжение
двумя администраторами. Подробные правила и последовательность есть в backend
`docs/users-bulk-actions.md`.
